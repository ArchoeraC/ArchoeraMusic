### 索引体积外推

- A（含拼音）search.db = **74.6 MiB** @ 10000 曲 → 外推 @25000 曲 ≈ **187 MiB**（§2.2 预算 100–300 MB）✅ 达标
- B（无拼音）search.db = **45.7 MiB** @ 10000 曲 → 外推 ≈ **114 MiB**
- A 体积构成（`dbstat`）：元数据表 `search_docs` 0.3 MiB + FTS 倒排（`search_fts_data` 69.5 MiB + `_idx` 0.0 MiB + `_docsize` 0.2 MiB）；`track_id` 文本合计仅 0.1 MiB。
  B（无拼音）构成：元数据表 0.3 MiB + 倒排 `search_fts_data` 40.8 MiB —— 拼音列令 A 比 B 多 29 MiB。
- contentless v2 说明：`search_fts` 以 `content=''` + `contentless_delete=1` 建表，倒排只存 postings / 位置，**不再把 token 文本另存一份**；体积构成由「内容表 + 倒排」变为「元数据表 + 倒排」。
- 全量耗时（A，取最快轮 `durationMs`）@ 10000 曲 = **12.3s** → 外推 @25000 曲 ≈ **31s**（预算 120–300s）✅ 达标
- 全量耗时（B，无拼音）@ 10000 曲 = **9.7s**（拼音列生成是 A/B 主要差异）
- 峰值 RSS（A）≈ **86 MiB**（预算「≤ 数百 MB」）✅ 达标

> ⚠ 本环境（WSL2 虚拟磁盘）`/proc/<pid>/io` 的 `write_bytes` 恒为 0，**写入量数据不可用**；写局部性 / 磨损只能间接评估（世代化顺序写 + dirty-only 增量）。

### 修订记录：contentless v2（schema_version=2 / analyzer_version=2）

针对首版 P5 报告暴露的两处缺陷做的修订（**同为本次一次跑出的数据**）：

1. **索引体积超预算** → `search_fts` 由 external-content 改为 **contentless**（`content=''` + `contentless_delete=1`），`search_docs` 仅保留元数据、不再存 token 文本；列序 / bm25 权重序不变，`MATCH` 列过滤、短语、`bm25()` 语义不变。
2. **NFKC 不完整** → `Analyzer` 归一化由手写全角折叠升级为**逐字符 NFKC 兼容折叠**（离线表 `data/nfkc.tsv`，仅 BMP、逐字符）：`ﬁ`→`fi`、`①`→`1`、相容表意字折叠等；因词元输出变化，`AnalyzerVersion` 1 → 2（旧库版本不符 → 全量重建）。

## 7. P5 判定（§5.5 自研段引擎）

**结论：P5 不触发 → 自研段引擎（§5.5 实现 B）不实施。**

判定依据（严格对齐 §5.5 的触发条件：**FTS5 在目标介质上 checkpoint 随机回写导致 locality / 磨损不达标**）：
1. **存储/查询性能达标**：全量外推 ≈ 31s（≤ 5min）、查询合计 P50/P95 9.400/41.030ms（远低于 20/80ms）、增量秒级（K=20 → 975ms）、峰值 RSS 86MB —— 存储引擎能力本身**无短板**。
2. **写局部性对策已生效**（§5.3/§7.2）：全量为「临时世代从零**顺序写** + fsync + 原子 rename」，增量按 **dirty-only** 且收尾 `wal_checkpoint(TRUNCATE)`；构建与增量耗时未见随机写病理。
3. **无 locality / 磨损不达标的测量证据** → §5.5 的前提不成立，按设计「**先量再定、不先验假设**」原则，自研段引擎**无测量支撑，不实施**。

> 注意：本结论受 §8 局限约束，尤其**磨损 / 长期写放大未量化**（`write_bytes` 在本 WSL2 环境不可用）。若后续在 HDD（或高写入敏感的 eMMC）上实测出现 locality / 磨损不达标，P5 仍按 §5.5 条件触发。

## 8. 局限

1. **规模外推**：本机实测 N=10000；25k 数据为 **线性外推**（构建耗时、索引体积随 N 近似线性，但 FTS 段合并/页分配有次线性效应，外推偏保守）。未直接跑 25k（本机内存 7.6 GB / 盘可承载，为控时长未做）。
2. **介质**：工作盘为 `/dev/sdd`（ext4，`/sys/.../rotational=1`，在 WSL2 上）；§7.2 的「checkpoint 随机回写」痛点主要在**物理 HDD**，本环境为 WSL2 虚拟磁盘，**不能等同于真机 HDD**，且 `write_bytes` 不可用 → 写入量/磨损未直接量化。
3. **未测磨损 / 长期度**：单轮 bench 无法反映多世代、反复增量后的碎片与写放大；未做 `iostat`/闪存擦除块级观测。
4. **索引体积对语料敏感**：本语料按 §8 口径取 2–8 KB/曲（均 5 KB、密集中文）。语料越短/越稀疏，`search_docs` 与倒排的固定开销占比越高；外推基于本语料分布。
5. **查询集规模**：代表查询 7 条（中文子串/短语/繁体/拼音连写/首字母/拉丁前缀/整词），非完整 §8 标注集；未测召回@k / MRR / NDCG（那是 P0 分析器评估，非本 P5 性能问题）。
6. **查询语义**：harness 的 MATCH 构造（中文仅词元 AND；拉丁整词前缀；连写全拼按音节 AND 末音节前缀，OR 组合；首字母经 pinyin 列命中）对齐设计 §4 与既有 E2E，但 P3 Dart 查询层尚未落地，最终表达式可能微调（影响召回，不影响延迟量级）。
7. **峰值内存**：`VmHWM` 轮询（20 ms）可能略低估瞬时峰值；索引器为 run-to-completion 同步模型，无等待式竞态判定（符合 AGENTS.md）。
