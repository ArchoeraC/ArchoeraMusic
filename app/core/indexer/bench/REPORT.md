## 4. 增量（非 --full）

| 场景 | 脏曲 K | wall ms | durationMs | 峰值 RSS MB | indexed | deleted |
|---|---|---|---|---|---|---|
| 零脏曲（no-op） | 0 | 326 | 278 | 59 | 0 | 0 |
| 改 file_mtime | 20 | 7663 | 7603 | 141 | 20 | 0 |
| 改 file_mtime | 200 | 17860 | 17803 | 140 | 200 | 0 |
| 零脏曲（no-op，**含 .lrc 档**） | 0 | 326 | 281 | 59 | 0 | 0 |

- **零脏曲 = 278ms**：这是增量的**固定开销**（阶段一探测 + 收尾写路径），**不含任何内容读取**。K=20 与它的差值才是脏曲写路径成本。
- K=20 → 7603ms；K=200 → 17803ms：ΔK=180 增加 10200ms（**边际 ≈ 56.7ms/曲**）——脏曲部分随 K 近似线性。
- 归因：K=20 相对零脏曲多 7325ms，即 20 首脏曲的「取内容 + 分析 + FTS 删除/写入 + 收尾 checkpoint」成本；**阶段一探测本身很轻**（零脏曲已含它）。
- 增量预算（「秒级、≈ K 成正比」）❌ 超标。
- `.lrc` 档零脏曲增量 = **281ms**：与不开启时同量级即说明**索引器没有任何文件系统侧车探测**（侧车锚点 `lrc_mtime/size` 来自扫描器写入的`library.db` 列，见设计文档 §4.4）；若显著变大，先查 `library.db` 是否缺列（缺列会降级为「无侧车」，不会变慢）或扫描器是否未写侧车。

>
> ⚠ **候选集上限机制已于 2026-11-12 撤销**：原实现 `WHERE rowid IN (SELECT … MATCH ? LIMIT 5000)` 会让 FTS5 的 `bm25()` 在无 `MATCH` 的外层查询里**静默返回 0**，相关性排序整体失效（且并不更快）。现一律 `WHERE search_fts MATCH ? ORDER BY bm25(...) LIMIT ?` 全排序；`--cap` 仍可传但不再影响结果。详见设计文档 §4.5 与 `SearchLayerTests.RankingIntegrity`。

| 指标 | 预算 | 实测（本机 @30000 曲） | 外推 @25000 曲 | 结论 |
|---|---|---|---|---|

| 增量（K 首） | ≈ K 成正比，秒级 | 零脏曲 278ms；K=20 → 7603ms；K=200 → 17803ms | 边际 ≈ 线性 | ❌ 超标 |

## 7. P5 判定（§5.5 自研段引擎）

**结论：P5 不触发 → 自研段引擎（§5.5 实现 B）不实施。**

判定依据（严格对齐 §5.5 的触发条件：**FTS5 在目标介质上 checkpoint 随机回写导致 locality / 磨损不达标**）：
1. **存储侧未见短板**：全量 118.0s（含 .lrc 119.5s）（≤ 5min）、增量零脏曲 278ms、峰值 RSS 184MB、索引 382.5MiB（30000 曲）。
2. **写局部性对策已生效**（§5.3/§7.2）：全量为「临时世代从零**顺序写** + fsync + 原子 rename」，增量按 **dirty-only** 且收尾 `wal_checkpoint(TRUNCATE)`；构建与增量耗时未见随机写病理。
3. **无 locality / 磨损不达标的测量证据** → §5.5 的前提不成立，按设计「**先量再定、不先验假设**」原则，自研段引擎**无测量支撑，不实施**。

⚠ **查询延迟超标**（非存储引擎问题，自研段引擎也不解决）。最慢一条 `wan`（pinyin_initials）P50 71.6ms；pooled P50/P95 = 32.6/70.7ms （LIMIT=10000）。根因：FTS5 `ORDER BY bm25` 必须给**全部命中**打分（`LIMIT` 只能在很宽区间小额削减：实测 10000→300 仅省 ~25%，放到 LIMIT=50 的 P50 地板仍有 25.1ms → **降 limit 修不好本项超标**），而**宽命中集支**——拼音音节前缀 / 首字母前缀 / 跨语言候选（T1，`愛`→`love` 一类高频英文词）——会把命中集放大。
本档已用**大词表语料**（命中率贴近真实曲库），故上述超标**值得跟进**；收敛方向：查询编译侧降低命中宽度、跨语言候选的选择性门控、或自研可剪枝的打分器（需先建立与 FTS5 分数一致性的金标准）。
另注：本版数字**不含**已撤销的候选集上限（旧版用错误写法换来的「更快」实为排序失效）。

> 本结论受 §8 局限约束；磨损 / 长期写放大未量化（单轮 bench 不反映多世代碎片与写放大）。

## 8. 局限

1. **规模**：本报告为 N=30000 的**直接实测**（≥ §2.2 的 25k 目标点）。
2. **介质**：工作盘为 `/dev/sdd`（ext4，`HDD(rotational)`，挂载 `/`）。§7.2 的「checkpoint 随机回写」痛点主要在**物理 HDD / eMMC**；本环境 `write_bytes` 可用（A 档写 3298MB），但未做擦除块级观测。
3. **未测磨损 / 长期度**：单轮 bench 无法反映多世代、反复增量后的碎片与写放大；未做 `iostat` / 闪存块级观测。
4. **语料仍是合成数据**：本档用 4000 词随机字表构造歌词（单词命中率约 1–20%，比小词表档贴近真实），但**汉字分布是均匀的**——真实中文高频字（的 / 我 / 你 / 爱）远比生僻字常见。因此**单字查询**（如 `愛` / `你`）在本档的命中率会显著高于真实曲库，其延迟仍偏保守；词级 / 短语级查询的可迁移性更好。索引体积同理受词表基数影响：本档 382 MiB 高于小词表档的 218 MiB。
5. **查询集规模**：代表查询 14 条（中文子串 / 短语 / 繁体 / 中文+首字母 / 拼音连写 / 单音节拼音前缀 / 首字母 / 拉丁前缀 / 整词），非完整 §8 标注集；未测召回@k / MRR / NDCG（那是 P0 分析器评估，非本 P5 性能问题）。
6. **查询语义**：MATCH 构造与生产查询编译层 `app/core/indexer/SearchQuery.cs` 同构——词法支（CJK 连续 bigram 引号短语 + unigram `AND`、末拉丁 / 数字 `*`）、拼音支（单音节 `*` 前缀；**≥2 音节相邻短语**）、首字母支、跨语言支，各支 `OR`；LIMIT 覆盖 50、10000（后者 = 生产曲库页 `kSearchIndexRankLimit`）。召回质量不在本报告范围。
7. **峰值内存**：`VmHWM` 轮询（20 ms）可能略低估瞬时峰值；索引器为 run-to-completion 同步模型，无等待式竞态判定（符合 AGENTS.md）。
8. **版本锚点**：本报告数据对应 `schema_version=7` / `analyzer_version=12`、代码 `4907db78`；分析器 / schema 版本变动会令旧库全量重建，届时性能数字需重跑（本报告不含历史版本的对比数据）。
