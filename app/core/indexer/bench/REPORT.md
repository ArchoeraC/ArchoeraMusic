## 4. 增量（非 --full）

| 场景 | 脏曲 K | wall ms | durationMs | 本次合并 | 峰值 RSS MB | indexed | deleted |
|---|---|---|---|---|---|---|---|
| 零脏曲（no-op） | 0 | 306 | 253 | 否 | 59 | 0 | 0 |
| 改 file_mtime | 20 | 1427 | 1390 | 否 | 140 | 20 | 0 |
| 改 file_mtime | 200 | 18939 | 18882 | 是（含全段合并） | 141 | 200 | 0 |
| 零脏曲（no-op，**含 .lrc 档**） | 0 | 286 | 249 | 否 | 59 | 0 | 0 |

- **零脏曲 = 253ms**：这是增量的**固定开销**（阶段一探测 + 收尾写路径），**不含任何内容读取**（也不触发分析器初始化）。
- K=20 → 1390ms；K=200 → 18882ms：ΔK=180 增加 17492ms（名义边际 ≈ 97.2ms/曲）。
- ⚠ **该边际不是纯写路径成本**：K=200 那次**跨过了合并阈值**、含一次全段合并，而 K=20 那次没有。看「只写不合并」的成本请参考 K=20（或把 `--merge-every` 调大后复测）。
- K=20 相对零脏曲多 1137ms：其中**真实写入只要 13.5ms/20 首**（隔离实测），大头是**分析器首次初始化**（Unihan / 读音表 `Lazy<>` 冷加载 ≈1.1s，进程级一次性）——零脏曲不分析故不含它。「阶段一探测」本身很轻。
- 增量预算（「秒级、≈ K 成正比」）✅ 达标。
- **耗时构成（2026-11-12 定位）**：主导项曾是收尾的 FTS5 `optimize`（全段合并）——402MB 索引隔离实测 **4.5–13s**，且不随脏曲数缩小（只改 1 首也付全额），因为它重写整个倒排；真实写路径只要 13.5ms/20 首。另有约 **1.1s 是进程级一次性开销**（Unihan / 读音表的 `Lazy<>` 首次加载），与增量规模无关。
- **现状：改为按「累计改写曲数」触发合并**（`IndexerOptions.MergeEveryUpdates`，默认 30）。合并**不能不做**：跳过它会让 `contentless_delete` 的墓碑累积、宽命中查询退化（独立进程实测 `爱你`：20 曲 +34% / 60 曲 +73% / 120 曲 +103%，而排序结果不变）；但每次都做又太贵。阈值即两者的折中——常态增量只写不合并，累计约 30 首后的一次增量顺带合并。
- **分界很重要**：脏曲的*筛选与应用*始终是**同步、完整**的（阶段一探测 + 阶段二写入），合并只是物理整理——不改内容、失败也无损（索引仍然正确，下次增量再尝试），二者不可混为一谈。
- `.lrc` 档零脏曲增量 = **249ms**：与不开启时同量级即说明**索引器没有任何文件系统侧车探测**（侧车锚点 `lrc_mtime/size` 来自扫描器写入的`library.db` 列，见设计文档 §4.4）；若显著变大，先查 `library.db` 是否缺列（缺列会降级为「无侧车」，不会变慢）或扫描器是否未写侧车。

>
> ⚠ **候选集上限机制已于 2026-11-12 撤销**：原实现 `WHERE rowid IN (SELECT … MATCH ? LIMIT 5000)` 会让 FTS5 的 `bm25()` 在无 `MATCH` 的外层查询里**静默返回 0**，相关性排序整体失效（且并不更快）。现一律 `WHERE search_fts MATCH ? ORDER BY bm25(...) LIMIT ?` 全排序；`--cap` 仍可传但不再影响结果。详见设计文档 §4.5 与 `SearchLayerTests.RankingIntegrity`。

## 6. 对照 §2.2 预算

| 指标 | 预算 | 实测（本机 @30000 曲） | 外推 @25000 曲 | 结论 |
|---|---|---|---|---|
| 首次全量构建（含拼音 + `.lrc`） | ≤ 2–5 min | 104.2s（C 含 .lrc） | ≈ 87s | ✅ 达标 |
| 增量（K 首） | ≈ K 成正比，秒级 | 零脏曲 253ms；K=20 → 1390ms；K=200 → 18882ms | 边际 ≈ 线性 | ✅ 达标 |
| 查询 P50 / P95（pooled） | ≤ 20 / ≤ 80 ms | 30.204 / 69.722 ms（A, LIMIT=10000） | 与 N 近似无关* | ❌ 超标 |
| 查询 P50 / P95（逐条） | ≤ 20 / ≤ 80 ms | 存在超标（见 §5 ⚠） | 随命中集增长 | ❌ 超标 |
| 索引体积 | ~100–330 MB | 382.5 MiB（A） | ≈ 319 MiB | ✅ 达标 |
| 峰值内存 | ≤ 数百 MB，可限 | 181 MiB（A） | — | ✅ 达标 |

\* 「与 N 近似无关」只对**窄命中**查询成立；宽命中集（常见拼音 / 首字母）随 N 线性增长，见 §5 逐条表与 §8 局限。

\*\* 增量的耗时由 FTS5 `optimize`（全段合并，**O(索引)**）主导，与脏曲数无关；现按累计改写曲数触发（`MergeEveryUpdates`，默认 30），故 K=200 那次含合并、K=20 那次不含。详见 §4。

> 索引体积预算已按实测**校准**：原目标 100–300 MB 是实测前估数，实际外推 25000 曲 ≈ 319 MiB（超 6%），2026-11-12 复核接受，上限调整为 330 MB。理由：索引是磁盘上按需读取的派生数据、不常驻内存（峰值 RSS 181MB）；对照「全部歌词常驻内存」（GiB 级）已在数量级上更省；体积大头是拼音列（令 A 比 B 多 139 MiB），砍它要牺牲拼音召回。

➡ **结论**：pooled 口径超标，但**逐条口径存在超标**——最慢一条 `wan`（pinyin_initials）P50 70.0ms / P95 72.1ms。pooled 是被大量窄查询摊平的结果，**不应作为单条查询预算的判定口径**。

## 7. P5 判定（§5.5 自研段引擎）

**结论：P5 不触发 → 自研段引擎（§5.5 实现 B）不实施。**

判定依据（严格对齐 §5.5 的触发条件：**FTS5 在目标介质上 checkpoint 随机回写导致 locality / 磨损不达标**）：
1. **存储侧未见短板**：全量 109.1s（含 .lrc 104.2s）（≤ 5min）、增量零脏曲 253ms、峰值 RSS 181MB、索引 382.5MiB（30000 曲）。
2. **写局部性对策已生效**（§5.3/§7.2）：全量为「临时世代从零**顺序写** + fsync + 原子 rename」，增量按 **dirty-only** 且收尾 `wal_checkpoint(TRUNCATE)`；构建与增量耗时未见随机写病理。
3. **无 locality / 磨损不达标的测量证据** → §5.5 的前提不成立，按设计「**先量再定、不先验假设**」原则，自研段引擎**无测量支撑，不实施**。

⚠ **查询延迟超标**（非存储引擎问题，自研段引擎也不解决）。最慢一条 `wan`（pinyin_initials）P50 70.0ms；pooled P50/P95 = 30.2/69.7ms （LIMIT=10000）。根因：FTS5 `ORDER BY bm25` 必须给**全部命中**打分（`LIMIT` 只能在很宽区间小额削减：实测 10000→300 仅省 ~25%，放到 LIMIT=50 的 P50 地板仍有 25.1ms → **降 limit 修不好本项超标**），而**宽命中集支**——拼音音节前缀 / 首字母前缀 / 跨语言候选（T1，`愛`→`love` 一类高频英文词）——会把命中集放大。
本档已用**大词表语料**（命中率贴近真实曲库），故上述超标**值得跟进**；收敛方向：查询编译侧降低命中宽度、跨语言候选的选择性门控、或自研可剪枝的打分器（需先建立与 FTS5 分数一致性的金标准）。
另注：本版数字**不含**已撤销的候选集上限（旧版用错误写法换来的「更快」实为排序失效）。

> 本结论受 §8 局限约束；磨损 / 长期写放大未量化（单轮 bench 不反映多世代碎片与写放大）。

## 8. 局限

1. **规模**：本报告为 N=30000 的**直接实测**（≥ §2.2 的 25k 目标点）。
2. **介质**：工作盘为 `/dev/sdd`（ext4，`HDD(rotational)`，挂载 `/`）。§7.2 的「checkpoint 随机回写」痛点主要在**物理 HDD / eMMC**；本环境 `write_bytes` 可用（A 档写 3639MB），但未做擦除块级观测。
3. **未测磨损 / 长期度**：单轮 bench 无法反映多世代、反复增量后的碎片与写放大；未做 `iostat` / 闪存块级观测。
4. **语料仍是合成数据**：本档用 4000 词随机字表构造歌词（单词命中率约 1–20%，比小词表档贴近真实），但**汉字分布是均匀的**——真实中文高频字（的 / 我 / 你 / 爱）远比生僻字常见。因此**单字查询**（如 `愛` / `你`）在本档的命中率会显著高于真实曲库，其延迟仍偏保守；词级 / 短语级查询的可迁移性更好。索引体积同理受词表基数影响：本档 382 MiB 高于小词表档的 218 MiB。
5. **查询集规模**：代表查询 14 条（中文子串 / 短语 / 繁体 / 中文+首字母 / 拼音连写 / 单音节拼音前缀 / 首字母 / 拉丁前缀 / 整词），非完整 §8 标注集；未测召回@k / MRR / NDCG（那是 P0 分析器评估，非本 P5 性能问题）。
6. **查询语义**：MATCH 构造与生产查询编译层 `app/core/indexer/SearchQuery.cs` 同构——词法支（CJK 连续 bigram 引号短语 + unigram `AND`、末拉丁 / 数字 `*`）、拼音支（单音节 `*` 前缀；**≥2 音节相邻短语**）、首字母支、跨语言支，各支 `OR`；LIMIT 覆盖 50、10000（后者 = 生产曲库页 `kSearchIndexRankLimit`）。召回质量不在本报告范围。
7. **峰值内存**：`VmHWM` 轮询（20 ms）可能略低估瞬时峰值；索引器为 run-to-completion 同步模型，无等待式竞态判定（符合 AGENTS.md）。
8. **版本锚点**：本报告数据对应 `schema_version=7` / `analyzer_version=12`、代码 `e2901785`；分析器 / schema 版本变动会令旧库全量重建，届时性能数字需重跑（本报告不含历史版本的对比数据）。
9. **跨机器基线不可直接比较**：机器环境随本次实测记录于 §1（8 逻辑核 / 7.59 GB / HDD(rotational)）。与**上一版报告**的绝对延迟差异**不构成回归或改善的证据**——CPU 核数、内存与介质（HDD vs NVMe）都会主导全量构建与宽命中查询的耗时。只有**同一版内部**的 A/B 对照（拼音列开 / 关）与同机多次采样才可相互比较。
