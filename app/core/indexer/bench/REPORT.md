## 4. 增量（非 --full）

| 场景 | 脏曲 K | wall ms | durationMs | 峰值 RSS MB | indexed | deleted |
|---|---|---|---|---|---|---|
| 零脏曲（no-op） | 0 | 202 | 157 | 61 | 0 | 0 |
| 改 file_mtime | 20 | 2789 | 2747 | 153 | 20 | 0 |
| 改 file_mtime | 200 | 5045 | 5012 | 153 | 200 | 0 |
| 零脏曲（no-op，**含 .lrc 档**） | 0 | 202 | 163 | 62 | 0 | 0 |

- **零脏曲 = 157ms**：这是增量的**固定开销**（阶段一探测 + 收尾写路径），**不含任何内容读取**。K=20 与它的差值才是脏曲写路径成本。
- K=20 → 2747ms；K=200 → 5012ms：ΔK=180 增加 2265ms（**边际 ≈ 12.6ms/曲**）——脏曲部分随 K 近似线性。
- 归因：K=20 相对零脏曲多 2590ms，即 20 首脏曲的「取内容 + 分析 + FTS 删除/写入 + 收尾 checkpoint」成本；**阶段一探测本身很轻**（零脏曲已含它）。
- 增量预算（「秒级、≈ K 成正比」）✅ 达标。
- `.lrc` 档零脏曲增量 = **163ms**：与不开启时同量级即说明**索引器没有任何文件系统侧车探测**（侧车锚点 `lrc_mtime/size` 来自扫描器写入的`library.db` 列，见设计文档 §4.4）；若显著变大，先查 `library.db` 是否缺列（缺列会降级为「无侧车」，不会变慢）或扫描器是否未写侧车。

>
> 查询侧另有**候选集上限**（生产默认 5000，`--cap 0` 可关闭做对照）：`WHERE rowid IN (SELECT rowid … MATCH ? LIMIT 5000)` 先取有界候选再 bm25 排序——`ORDER BY bm25` 否则要给全部命中打分；窄命中（候选 < 上限）不受影响。

## 6. 对照 §2.2 预算

| 指标 | 预算 | 实测（本机 @30000 曲） | 外推 @25000 曲 | 结论 |
|---|---|---|---|---|

| 增量（K 首） | ≈ K 成正比，秒级 | 零脏曲 157ms；K=20 → 2747ms；K=200 → 5012ms | 边际 ≈ 线性 | ✅ 达标 |

| 索引体积 | ~100–300 MB | 218.0 MiB（A） | ≈ 182 MiB | ✅ 达标 |
| 峰值内存 | ≤ 数百 MB，可限 | 195 MiB（A） | — | ✅ 达标 |

➡ **结论**：pooled 口径达标，但**逐条口径存在超标**——最慢一条 `我爱你`（cjk_with_initials）P50 24.9ms / P95 25.1ms。pooled 是被大量窄查询摊平的结果，**不应作为单条查询预算的判定口径**。

## 7. P5 判定（§5.5 自研段引擎）

**结论：P5 不触发 → 自研段引擎（§5.5 实现 B）不实施。**

判定依据（严格对齐 §5.5 的触发条件：**FTS5 在目标介质上 checkpoint 随机回写导致 locality / 磨损不达标**）：
1. **存储侧未见短板**：全量 36.0s（含 .lrc 39.0s）（≤ 5min）、增量零脏曲 157ms、峰值 RSS 195MB、索引 218.0MiB（30000 曲）。
2. **写局部性对策已生效**（§5.3/§7.2）：全量为「临时世代从零**顺序写** + fsync + 原子 rename」，增量按 **dirty-only** 且收尾 `wal_checkpoint(TRUNCATE)`；构建与增量耗时未见随机写病理。
3. **无 locality / 磨损不达标的测量证据** → §5.5 的前提不成立，按设计「**先量再定、不先验假设**」原则，自研段引擎**无测量支撑，不实施**。

⚠ **独立于 P5 的问题：查询延迟超标**（非存储引擎问题，自研段引擎也不解决）。最慢一条 `我爱你`（cjk_with_initials）P50 24.9ms；pooled P50/P95 = 11.6/24.9ms （LIMIT=10000）。根因：FTS5 `ORDER BY bm25` 必须给全部命中打分，而**短前缀支（首字母 / 拼音音节前缀，且首字母与拼音同列）**与**跨语言候选支（T1，`愛`→`love` 一类高频英文词）**都会把命中集放大到接近整库。收敛方向应在**查询编译 / schema 层**（首字母独立列、前缀长度门控、跨语言候选的选择性门控 / 渐进式合并、命中集上限），并另立优化项跟进。

> 本结论受 §8 局限约束；磨损 / 长期写放大未量化（单轮 bench 不反映多世代碎片与写放大）。

## 8. 局限

1. **规模**：本报告为 N=30000 的**直接实测**（≥ §2.2 的 25k 目标点）。
2. **介质**：工作盘为 `/dev/nvme2n1p2`（btrfs，`SSD/NVMe(non-rotational)`，挂载 `/home`）。§7.2 的「checkpoint 随机回写」痛点主要在**物理 HDD / eMMC**；本环境 `write_bytes` 可用（A 档写 1989MB），但未做擦除块级观测。
3. **未测磨损 / 长期度**：单轮 bench 无法反映多世代、反复增量后的碎片与写放大；未做 `iostat` / 闪存块级观测。
4. **索引体积 / 查询命中集对语料敏感**：本语料按 §8 口径取 2–8 KB/曲（均 5 KB、密集中文），但**词表很小**（固定词表拼装）——于是常用词元几乎出现在每一首里（`我` / `爱` / `你` / `love` / `hello` 等命中 2.8 万–3 万 / 3 万）。真实曲库的常用词元命中集会窄得多，故本报告的**宽命中查询延迟应视为上界**；窄命中查询（短语 / 长音节组合）与 N 的关系才是可迁移的结论。索引体积同理：语料越短 / 越稀疏，元数据表与倒排的固定开销占比越高。
5. **查询集规模**：代表查询 9 条（中文子串 / 短语 / 繁体 / 中文+首字母 / 拼音连写 / 单音节拼音前缀 / 首字母 / 拉丁前缀 / 整词），非完整 §8 标注集；未测召回@k / MRR / NDCG（那是 P0 分析器评估，非本 P5 性能问题）。
6. **查询语义**：MATCH 构造与生产查询编译层 `search_query.dart` 同构——词法支（CJK 连续 bigram 引号短语 + unigram `AND`、末拉丁 / 数字 `*`）、拼音支（单音节 `*` 前缀；**≥2 音节相邻短语**）、首字母支、跨语言支，各支 `OR`；LIMIT 覆盖 50、10000（后者 = 生产曲库页 `kSearchIndexRankLimit`）。召回质量不在本报告范围。
7. **峰值内存**：`VmHWM` 轮询（20 ms）可能略低估瞬时峰值；索引器为 run-to-completion 同步模型，无等待式竞态判定（符合 AGENTS.md）。
8. **版本锚点**：本报告数据对应 `schema_version=5` / `analyzer_version=6`、代码 `bfe2dd58`；分析器 / schema 版本变动会令旧库全量重建，届时性能数字需重跑（本报告不含历史版本的对比数据）。
