ArchoeraMusic 媒体处理
  • ① 播放（内核 EraAudio）
    • Dart 编排：PlaybackNotifier · resolvePlaySource SourcePlatform 注册表：NT/KG/QQ/Neko/local/streaming
    • C 壳 pipeline.c：会话 · PCM 落盘或内存 · miniaudio 自播 · 事件 FIFO
    • 传输：本地路径 · mem（SegStore 内存源） · cb（宿主 AVIO） · 原生 HTTP(S)（kernel/net.zig，在线直链优先） 宿主注入为回退基线
    • 解码：EraAudio（已接管格式 flac/mp3/aac/opus/vorbis/mka/dts/tta/spx/shn/mpc…） ↔ FFmpeg 兜底
    • DSP：EQ / limiter / loudness（kernel/dsp；B 档向量化，与 C 逐位一致）
    • 频谱：libfft.so（Dart 拉窗）
    • EraSync 常驻池 pool：zk_submit（decode/metadata，事件推）· zk_engine_* 流式会话（分块串行，max_streams）· 弹性扩容 cap=max_workers（submit 只提示、Master 异步补建、满即拒）· AS3 调节器 · AS2 pinned 1:1（门控）
  • ② 扫描（内核 + 扫描器）
    • Dart → C# ScannerEngine（NativeAOT）：触发/进度/结果
    • 目录遍历 → Parallel.For 并行解析 · 并行度 = AdaptiveConcurrency.ForIOBound()
    • 每文件元数据：TagLibSharp（主路径，多数格式） / zk_metadata_open（同步直桥，native probe：容器/编码/时长/标签/首图）
    • 写：有界 BlockingCollection + 专用写线程 → 批量事务 → SQLite library.db WAL · synchronous=NORMAL
    • 协商：SetConcurrency(_maxParallelism) → zk_metadata_set_concurrency(n) —— 内核只存（g_meta_concurrency），不调度/不限流
    • 旁路原生模块：刮削(C++, TagLib+libcurl) · 下载(Rust) · Subsonic(Go)
    • 写分配：两级生产者/消费者 + 自适应攒批 scanner 写路径
      • L1 解析线程（Parallel.For，N=_maxParallelism）产出 TrackMetadata → BlockingCollection<TrackMetadata>(1024)（满=背压）
      • L2 scanner-writer 攒批：批量由 AdaptiveBatchSize 动态定 （目标 ~300ms/批，10..10000 + 内存上限）→ FlushBatch → StageTracksAsync 必须快照（new List(...)，因 L2 立即 Clear 复用 batch）
      • L3 SqliteDirectWriter 专用写线程：BlockingCollection<Action>(4096)（背压） · 单写连接 · 每批单事务 INSERT 到 _scanner_stage_tracks
      • 最终合并：单事务 INSERT INTO tracks … ON CONFLICT(id) DO UPDATE（stage → 正式表）
      • 读：独立 _readConn + System.Threading.Lock（WAL 读写并发）；PRAGMA WAL + synchronous=NORMAL
      • 封面 ${id}.img 写盘在解析线程（TryWriteCover），不归写线程 待议：去封面写入化
      • 失败：写线程异常 → stderr 后继续（不静默）；FlushBatch 计 Errors；Flush() 排空队列
  • ③ 边界与红线
    • 在线传输：宿主注入（FFmpeg AVIO，cb）为回退基线；内核原生 HTTP(S)（kernel/net.zig，2026-10-01）为可选优先——socket/TLS/Range/重定向由 zk_decoder_open_url 自持，失败回退宿主 → FFmpeg；ARCHOERA_ERA_NATIVE_HTTP=0 可关闭
    • 扫描元数据不进池：同步直桥 → 不占 EraSync 槽；与播放仅 CPU/内存/磁盘/网络竞争
    • 播放池有界：线程 ≤ max_workers(+1 Master)；快速任务要么早停、要么到 cap 即拒
    • QoS 缺口：全局队列 FCFS、无优先级/无抢占 → 批量可能拖累播放；AS4（播放优先/保留 worker/批量节流）未做
    • ABI 不变：archoera_mediaengine.h 导出 / JSON 协议 / libfft.so / stream.wav|.pcm（P5）；内核符号 era_ 前缀；系统能力走 app/native/platform
  • ④ 扫描器「爆改」为什么快（约 +10~30%） 提交 29246d8 · 7a9e449 · 3b84419 · b6e535e
    • 彻底去 async：Channel<Action>+Task writeLoop → BlockingCollection + 专用写线程 29246d8
      • 根因：解析是 CPU-bound + 阻塞 IO，async/await 只产生状态机/TCS/线程池调度开销，没有并发收益
      • Parallel.ForEachAsync → Parallel.For：每文件不再生成 async 状态机 7a9e449
      • 全链路同步：UnmanagedCallersOnly 直接同步调用（去掉 Task.Run 跳转） 3b84419
    • 写路径串行化：单写线程 + 批量事务 + PRAGMA synchronous=NORMAL → 少 BUSY/少 fsync；读走独立连接 + WAL 并发；读锁换 .NET9 System.Threading.Lock
    • 内核元数据直桥：结构化 C ABI、零 JSON、一次取回标量+标签+首图；TagLib 不支持的格式统一解析 009ca55
    • 实测（1000 小文件，b6e535e）： wall 151.1 → 137.7 ms · files/s 6619 → 7261（+10%） · CPU 0.260 → 0.202 s（−22%） · RSS 70.4 → 68.4 MB
    • 另：425 文件 × 16 格式的 kernel(TagLib) 联动基准（6b79d70）：吞吐 199–238ms vs 196–226ms（持平），正确性 0 不一致——直桥的价值在统一解析与更低内存，而非小文件吞吐
